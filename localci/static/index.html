On-demand Docker capacity

Each active PR gets its own isolated worker. Containers start when queued work needs them and are removed at completion. Changing these settings affects newly started runs. Lower limits let existing runs finish.

Failed runs are not retried automatically. This cap also applies to Retry and bulk reruns: 2 retries means 3 total attempts for the same PR head and base commits. A new head or base starts a new revision budget. Active runs can finish when you lower the limit.

Speed up a run: increase Parallel jobs in its repository settings. Independent jobs can share this worker’s CPU/memory.
Speed up the queue: increase Simultaneous PR runs only while the displayed host-capacity plan fits.
Image loading and dependency downloads take time too. More parallel work can increase disk contention; compare duration and CPU usage in Analytics before increasing again.

REPOSITORY SETTINGS

Open, non-draft PRs from this repository run on configured worker in disposable Docker containers. Fork PRs are excluded.

When off, PRs opened by bots such as dependency updaters are recorded as blocked until you review them and start the run from the dashboard.

1. Choose what runs locally

GitHub file, local execution. A path such as .github/workflows/ci.yml identifies a workflow in your repository. By default, we fetch it from the PR’s base commit and run its checks on the merged PR code, entirely on configured worker. GitHub supplies source and receives results; it supplies no compute.

Use Edit local copy to keep a separate version here. Saving creates a local revision; it never commits or pushes YAML to GitHub. Existing queued/running jobs keep their snapshot. Use Retry for a new run with your saved settings.

Loading workflows…

After checkout, CI and review start independently in separate containers. Review inspects the diff using your model provider. Its credentials stay separate from CI jobs. Model-provider charges still apply.

Below-threshold findings remain visible and do not fail CI. Blocking findings, incomplete reviews and execution errors still require attention. This setting is saved with each new run; changing it does not change existing runs.

2. Speed and timeout

Independent jobs and matrix entries can run together; needs: dependencies still wait. Steps within a job run in order. Selected workflow files run in order; mergeCraft runs alongside them. CI and review split this run’s CPU/memory budget. The review timeout stops long AI reviews; timeouts stay failed, not passed. To run different PRs together, open Execution settings.

GitHub access for CI jobs

The host login supplies github.token and secrets.GITHUB_TOKEN for checkout, private dependencies, and tools such as Trivy. No new key is required. This is your account token: enabled CI jobs and PR code can use its existing GitHub permissions. Only enable this for repositories and contributors you trust. It is masked in logs and never sent to mergeCraft review. Run ./login.sh on configured worker to refresh it after reauthentication.

3. Non-secret workflow variables

These supply vars.NAME in YAML. For example, RUN_CODEQL = false disables a job guarded by vars.RUN_CODEQL == 'true'. Use the exact names your workflow references. Leave this empty if it uses no variables. API keys and passwords belong below.

Advanced: edit variables as JSON

An object mapping names to strings, for example {"RUN_CODEQL":"false"}. Apply JSON replaces the rows above.

4. Local credentials

CI workflows: passwords/tokens used by tests or build steps through secrets.NAME. Only provide credentials your selected workflow actually needs.
Review only: the provider settings/API key mergeCraft uses to call its model. These never enter CI containers.

GITHUB INTEGRATION

Connect your mergeCraft App

Open GitHub App settings ↗ and edit your mergeCraft App. Copy its numeric App ID. Under Credentials → Key pairs → New key, download a PEM file. Keep existing keys so your current integration continues working.

Under Permissions & events, Checks must be Read and write. In the App installation settings, include each repository you want to enable.

The key is encrypted on configured worker and never sent to build containers. Until connected, Local CI publishes commit statuses using your GitHub login.
