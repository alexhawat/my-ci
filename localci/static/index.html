On-demand Docker capacity

Each active PR gets its own isolated worker. Containers start when queued work needs them and are removed at completion. Changing these settings affects newly started runs. Lower limits let existing runs finish.

Failed runs are not retried automatically. This cap also applies to Retry and bulk reruns: 2 retries means 3 total attempts for the same PR head and base commits. A new head or base starts a new revision budget. Active runs can finish when you lower the limit.

Speed up a run: increase Parallel jobs in its repository settings. Independent jobs can share this worker’s CPU/memory.
Speed up the queue: increase Simultaneous PR runs only while the displayed host-capacity plan fits.
Image loading and dependency downloads take time too. More parallel work can increase disk contention; compare duration and CPU usage in Analytics before increasing again.

Reporting results to GitHub
Local CI tells GitHub the result of every local run so it shows on the pull request. This works without any GitHub App.
Optional: publish Check Runs with a GitHub App
Without an App, Local CI posts a local-ci commit status using the worker's GitHub login. With an App, it publishes a local-ci Check Run instead, shown under the App's name in the pull request's Checks tab with a line per check. Any GitHub App you own works; it does not have to be a mergeCraft App, although one you already use for mergeCraft can be reused.
  1. Create a GitHub App ↗ or open your Apps ↗. Under Permissions, set Repository → Checks to Read and write. No webhook is needed.
  2. Install the App on each repository that runs checks here.
  3. Copy its numeric App ID. Under Private keys, generate a key and download the .pem file. Existing keys keep working.
The key is encrypted on this worker and never sent to build or review containers. A repository the App is not installed on still gets a commit status.

mergeCraft reviews each PR's diff with your model provider, in its own container, while CI runs. Adding it shows its options in Repositories → Configure, where you turn it on per repository and save a provider credential. Model-provider charges apply. Removing it turns review off in every repository; a repository that runs nothing but review needs a CI workflow, or to be turned off, first.
Your own checks: any GitHub Actions workflow with an on: pull_request trigger can run here. In Repositories → Configure, pick a file anywhere in the repository, upload one, or paste the YAML.
Syncing with GitHub
The worker asks GitHub for open pull requests every 60 seconds and for new repositories every 10 minutes. Check GitHub now, at the top right, asks right away: useful after creating a repository or opening a PR when you do not want to wait. Runs never depend on it.
