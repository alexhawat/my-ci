# Security policy

## Reporting vulnerabilities

Report vulnerabilities privately through GitHub private vulnerability reporting for this repository: open the **Security** tab and choose **Report a vulnerability** (<https://github.com/alexhawat/my-ci/security/advisories/new>). Include the affected revision and an impact summary. Do not open public issues for unpatched vulnerabilities, and do not include live credentials, private deployment details, or customer/project data in any report.

## Deployment trust boundary

PR code is effectively root on the host and can read every stored credential. CI workers use privileged Docker-in-Docker and share the host kernel. Each run's privileged CI worker is on its own Docker bridge network, which isolates the CI workers of concurrent runs from each other over the network but is not a host boundary. The review container is not attached to it: it uses Docker's default bridge and needs only outbound access to the model provider, so PR code in the CI worker has no direct network path to the review container. Enable only repositories and contributors you would trust with host-root access. With `LOCALCI_WORKER_RUNTIME=sysbox-runc`, CI workers are Sysbox system containers in a user namespace instead of `--privileged` containers. That removes the direct host-root equivalence of privileged Docker-in-Docker, but the worker still shares the host kernel, so a kernel or Sysbox flaw remains a path to the host: keep the same trust requirement. Fork PRs are not executed, but that does not make same-repository code safe.

Bot-authored PRs (GitHub user type `Bot` or a login ending in `[bot]`) are not run automatically: my-ci records a blocked run awaiting operator approval, and the operator starts it from the dashboard after reviewing the change. That approval covers only the revision of the held run; a retry is refused if the PR's head or base commit has changed since. A system-ended run (for example, one interrupted by a worker restart) of a bot-authored PR is re-queued automatically only if an operator had started that revision or `run_bot_prs` is on; otherwise a new held run awaits approval. The per-repository `run_bot_prs` setting (off by default) restores automatic runs and should stay off unless you trust that bot's changes with host-root access.

Use a dedicated single-user host. Keep the backend bound to loopback behind the documented authenticated ingress. Any local user or container able to reach port 8787 can forge the identity header. An alternative ingress must strip client-supplied identity headers and insert the authenticated `Tailscale-User-Login` value itself.

Use narrow credentials. Each workflow's secrets file holds only the secrets it references (all of them if it reads secrets dynamically, such as `toJSON(secrets)`) and exists in the worker only while it runs; between workflows of one run, every container of the nested Docker daemon is removed before the next workflow's secrets file is copied in. This limits exposure but is not a sandbox, since jobs of a workflow share it and PR code can read the data volume. GitHub App credentials are not passed to CI or review containers but are stored in that volume. The optional host GitHub login is not permission-narrowed by workflow YAML, and once `login.sh` has run its token file exists on the host whether or not a repository enables it; use a dedicated low-privilege GitHub account. Keep the Docker socket, runtime token, database encryption key, backups, and provider credentials out of public artifacts and logs.

The dashboard's **Update to latest** builds and starts whatever the deployment's `origin` serves on the update branch, with the execution worker's Docker socket, so it trusts that remote as much as a manual `git pull` and rebuild would. Like other dashboard writes, it requires the permitted Tailscale login and a matching `Origin`. It only fast-forwards, refuses a checkout with uncommitted tracked changes, and never starts while a run is active. Set `LOCALCI_SELF_UPDATE=0` to remove it.

## Supported versions

Security fixes are applied to the latest commit on `main`. Older commits and local forks should be reviewed and upgraded by their operators.
